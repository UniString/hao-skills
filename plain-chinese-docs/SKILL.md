# 平实中文技术文档

文档是写给接手的人看的，不是写给模型压缩用的。信息密度来自"术语定义一次、指代明确、删掉废话"，不来自中英夹杂和名词堆叠。

## 判断标准

写完一段，问自己：一个刚接手这个仓库的工程师，不翻其他文档，能不能一遍读懂？
读不懂的常见原因恰好是两种"高密度"假象：术语没解释，或者指代要跳三个文件才能解开。这两种都算没写好。

## 术语

- 行业通用英文词（API、schema、token、DTO、advisory lock、spike）直接用，第一次出现时补一句大白话说明它在这里指什么。
- 内部代号（如"阶段 S""Layer A""五断言""缺陷 A4"）首次出现必须用一句话解释它指什么；同一文档内后续可直接用。
- 一句话里未解释的内部代号超过两个，就拆句。
- 不自造中英混合词（"runtime 物化""赋能""对齐一下口径"）；能找到中文口语等价词就用。

## 句式

- 动词优先，砍名词化："进行 runtime 的物化" → "把 hermes-agent 装起来跑通"。
- 先结论后细节；一句话只说一件事。
- 警惕翻译腔：滥用"进行 / 基于 / 对于……而言 / X 化 / 赋能 / 拉通"；被动句能改主动就改。

## 指代

"按 X 裁决的 Y""见 31 号 Decision 17"这类引用，要么就地展开成一句话说明它定了什么，要么给出处链接并补一句内容概要。
读者不应该为了读懂一句话去翻三个文件。

## 改既有文档时的保真线

文风改写不等于内容改写。以下内容一字不动：

- 状态标记（Proposed / Partially Implemented / Accepted / Superseded 等）及可能被脚本解析的行（`Status:`、`Blocked by:`、`date:`、`pr:`、`commit:`）。
- 所有代码块、字段名、SQL、命令、数字、日期、账号端口等事实。
- 所有 markdown 链接的 URL、文件名、路径。
- 编号锚点本身（票据 31、Decision 17、阶段 S、缺陷 A4）。
- 表格里的数据行；表头与说明列的措辞可以顺。

写完后把改写稿与原文各检索一遍反引号片段、链接和上述标记，确认没有丢失或变形。
改写后行数应控制在原文的 0.8–1.3 倍：不为压缩而压缩，也不注水。

## 例子（取自真实事故）

改前：

> 隔离安装 hermes-agent 0.18.0（不写 Profile、不动现有运行时），产出可执行 runtime 的环境说明。Layer A 最小探针（31 号 Decision 17 定义）：单工具 Task/Run-scoped 注入 + 一次挂起 + 恢复五断言。

改后：

> 在隔离环境里装一份 hermes-agent 0.18.0（不写用户 Profile，也不碰正在跑的生产实例），整理出让它跑起来的环境说明。然后做一个最小验证实验（spike，即一次性技术验证，结论归档、代码不进主干；31 号票据 Decision 17 把它定为 Layer A——只验 agent 运行时本身的机制，不验 Studio 这边的集成）：给一次 Agent 运行临时挂上一个工具，让它调用到一半停下来等人工批准，批完后核对三件事——运行身份没变、执行的是原来那次调用而且只执行一次、不需要用户再发新消息就能从原处继续跑完。
